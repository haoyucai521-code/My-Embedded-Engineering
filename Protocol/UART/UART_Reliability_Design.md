# 板间 UART 协议可靠性设计要点（交接文档）

> 用途：给后续接手改造该板间 UART 协议的 Agent/工程师的上下文。
> 范围：协议结构与收发路径、已验证的可靠性设计、已知问题与改进建议。
> 约定：全文以"某多板 UART 总线系统"代称具体产品，不涉及公司特定协议细节。
> 依据：本文描述与线上实现对齐（`src/common/ComProtocol.c`），改协议前先读实现再改文档。

---

## 一、系统背景

- 多块控制板通过同一条 UART 总线通信（如 MAIN / DISPLAY / BACK 三块板）。
- 所有板共享**同一份协议实现**，各板只在自己的处理回调里按职责消费数据。
- 载荷采用 PID(TLV) 结构：`[PID][len][data]`，QUERY / UPDATE / CTRL 三类命令共用同一套属性语义。
- 通信波特率 38400，单帧上限 50 字节，其中数据区最大 44 字节。
- UART 接收配置 `needWakeup = true`：总线可作休眠唤醒源。

---

## 二、帧格式与协议要素

### 1. 帧格式

```
[PRE][SN][ADDR][CMD][LEN][DATA...][CHECKSUM]
```

| 字段 | 长度 | 说明 |
|------|------|------|
| PRE | 1B | 固定 `0xFA`，无字节转义 |
| SN | **1B 实际有效** | 序号，见下方"SN 位数事实" |
| ADDR | 1B | 目标地址或广播 |
| CMD | 1B | 命令码 |
| LEN | 1B | DATA 区长度 |
| DATA | 0~44B | PID(TLV) 载荷 |
| CHECKSUM | 1B | 前面所有字节 8bit 求和 |

### 2. 命令码

| 命令 | 码 | 方向 | 需 ACK | 说明 |
|------|----|------|--------|------|
| STATE_QUERY | 1 | MAIN→子板 | ✅ | 按 PID 列表查询 |
| STATE_UPDATE | 2 | 子板→MAIN | ✅ | 状态上报 |
| STATE_CTRL | 3 | MAIN→子板 | ✅ | 控制下发 |
| HB | 4 | MAIN→广播 | ❌ | 心跳/运行态广播 |
| ACK | 5 | 任意 | - | 应答 |

### 3. 地址

- MAIN `0x00`、DISPLAY `0x01`、BACK `0x02`
- 广播 `0xFF`（当前仅 HB 使用）

### 4. 关键事实：SN 声明 16bit、实际只发 8bit

- 协议字段类型声明为 `uint16_t`，但发送端自动序号是 `uint8_t` 自增，**写到帧里只占 1 字节**（截断为低 8 位）；接收端也只取 1 字节。
- 因此 SN 实际是 **8bit 回绕（0~255）**，不是 16bit。
- 在 38400bps + 去重窗口 500ms 下不会回绕冲突，但**文档必须与实现对齐**，改造时别按 16bit 去扩展，要么改类型、要么写清位数。

## 三、发送路径：入队 → 合并 → 重发

### 1. 需要 ACK 的包：入队后不立即发送

`STATE_QUERY/UPDATE/CTRL` 走 `ComProtocolSendPacket` 的 needAck 分支：**只入队，不立即写串口**。真正的发送由主循环定时驱动：

```
主循环 ComProtocolHandle():
  每 COM_RETRY_TIMEOUT(100ms) 检查一次：
    取队首包 → retryTimes++ → 写串口 → 若 retryTimes >= COM_RETRY_TIMES 删除
```

- 发送时机依赖**主循环调用 `ComProtocolHandle` 的频率**，不是调用发送 API 的时机。
- 每 100ms 最多发一个队首包，同一时刻只重发队首（串行）。

### 2. 合并门控：`retryTimes == 0`

- 相同地址 + 相同命令（仅 CTRL/UPDATE）+ `retryTimes == 0` + 合并后 ≤ 44B 的包合并进同一帧。
- **`retryTimes == 0` 意味着"尚未发出"**。包一旦发出 `retryTimes` 立即变 1。
- 原因：把已发出但未 ACK 的包合并进去，接收方会按去重规则丢掉，等于合并白做且丢业务。
- 这也是"入队不立即发送"带来的好处：入队到被主循环发出之间有一段合并窗口。

### 3. 队列上限 10，满则丢弃

- 队列长度 > 10 时新包直接丢弃（只打一条日志）。
- 对"最后状态为准"的 UPDATE 可接受；对 CTRL 静默丢一条 = 一次无响应。

### 4. 重发语义（关键，容易误解）

- `COM_RETRY_TIMES = 2`：一个包**最多发 2 次**（初始发送 + 1 次重发）。不是"重发 2 次"。
- 重发计时器是**全局共享**的，同一时刻只重发队首一个包。队列中靠后的包要等前面的包 ACK 或被删除后才轮到，最多被延迟 (队首数)×100ms。
- 收到 ACK：删除对应包并将计时器清零，下个主循环立即发下一个队首。

### 5. 广播帧（HB）：不入队、不重发、不 ACK

- HB 不在 needAck 列表，`ComProtocolSendPacket` 直接 `sendPacket` 写串口，**不进待 ACK 队列、不参与合并、不重发**。
- 丢失靠业务层兜底：周期补发 + 状态变化补发 + 开机主动查询（见心跳文档）。

## 四、接收路径：状态机 → ACK → 去重

### 1. 接收状态机

```
recvByte():
  字节间超过 500ms → 复位接收计数（半包丢弃）
  首个字节必须 0xFA，否则复位
  收到 6+LEN 字节（6 = 5 字节头 + 1 字节校验）→ 成帧
    校验和错误 → 丢弃并打 error 日志
    校验通过 → 交 handlePacket，复位计数
  接收缓冲溢出(≥100B) → 复位
```

- 帧定长由 `LEN` 决定（`6 + LEN`），LEN 被改坏时最坏要吃到最大长度或等 500ms 字节间超时才复位（见问题③）。
- **前导码过滤 + 500ms 字节间超时**是失步恢复的两个主机制。

### 2. 回 ACK 条件

`需要 ACK 的包` 且 `ADDR == 本板地址` 才回 ACK。广播包、非本板地址的包不回。

### 3. 去重：先回 ACK，再去重（顺序不能反）

收到重复帧时**仍然回 ACK**（让发送方停止重发），但**业务不重复处理**：

- 去重键 = `ADDR + SN + CMD`，三者一致且 500ms 内 → 忽略业务处理。
- 各地址独立记录去重状态，避免多板各自 SN 回绕互相误杀。
- 顺序反了（先判重再决定是否回 ACK）→ 重复帧不回 ACK → 发送方一直重发 → 死锁。

### 4. 业务处理：无入口地址过滤（风险点）

`handlePacket` 把成帧数据**无条件**交给 `ComProtocolPacketHandle`，不判断 `ADDR` 是否本板。各板靠 handler 内对不认识 PID 做 no-op 兜底：

- 发给 MAIN 的 CTRL，DISPLAY 也解析，但它的 handler 对非本板 PID 不动作。
- 当前能工作，但**入口没有地址过滤**意味着哪天有人往某个 handler 加了不判 PID 的分支，就会跨板误触发（见问题②）。

## 五、架构优点（改造时不要破坏）

1. **单份协议实现，多板复用**：帧解析、ACK、重发、去重全在共享代码，各板只做业务消费。不要在各板复制协议实现——一旦出现三份拷贝，改一处漏两处。
2. **PID(TLV) 解耦"传什么"和"怎么传"**：加新属性只加 PID 宏 + 各板 handler 分支，不碰帧格式。
3. **协议层不感知业务语义**：HB 只是第 4 号命令，心跳载荷怎么解读是业务层的事。协议层不关心 `data[0]` 是运行模式。

## 六、已知问题与改进建议（按优先级）

### ① 校验和太弱 → 换 CRC-16（安全相关，最优先）⚠️

- 现状：8bit 求和，只能防单比特错；偶数个比特翻转、字节交换都能漏过。
- 若系统涉及电机等安全动作，一帧被篡改可能误动作。
- 帧长 ≤50B，换 CRC-16 开销几乎可忽略。

### ② 接收端无地址过滤 → 入口加过滤

- 现状：所有板解析所有帧，靠各板 handler 对不认识的 PID 做 no-op 兜底。
- 风险：哪天有人往某个 handler 加了不按 PID 过滤的分支，就会跨板误触发。
- 建议：`handlePacket` 入口判断 `addr == 本板 || addr == 广播`，不匹配直接丢弃。

### ③ 失步恢复：LEN 位损坏拖长恢复窗口

- 帧定长依赖 `LEN`。LEN 被改坏成最大值时，解析器要吃到最大长度（50B）或等 500ms 字节间超时才复位，期间所有帧丢弃。
- 当前两个自愈机制：前导码过滤（下个合法帧从 `0xFA` 开始）＋ 500ms 字节间超时。
- 权衡：加字节转义 vs 缩短空闲复位窗口 vs 接受现状。若现场未出现明显丢帧，可接受但要知道代价。

### ④ SN 文档与实现漂移（维护地雷）

- 类型声明 16bit，实际只发/只读 8bit。
- 功能上 8bit + 500ms 去重窗口在 38400bps 下不会回绕冲突，但文档和代码必须对齐。
- 建议：文档写明实际位数，或把类型改真（注意改类型会改变帧结构，需全部板同步）。

### ⑤ 协议层 malloc/free，反复分配易碎小堆

- 合并路径每次 `malloc(新len)` + `free(旧块)`；入队也 malloc 包 + 数据。
- 小内存 MCU 长期跑会有碎片风险。
- 建议：静态池，或发送时直接从链表拷进固定 sendBuf。

### ⑥ 队列满静默丢弃

- 现状：队列 >10 时只打一条日志就丢弃。
- 对"最后状态为准"的 UPDATE 可接受；但对 CTRL 静默丢一条 = 一次无响应。
- 建议：CTRL 优先级高于 UPDATE；丢弃时打 warn 级日志。

### ⑦ 重发串行：队首优先，队尾被延迟

- 同一时刻只重发队首，每 100ms 处理一个包。队尾最坏被延迟 (队首数)×100ms。
- 在当前帧率（38400bps，一帧约 13ms）下 100ms 一个包足够，但如果业务把发送频率提高，队列会积压→满→丢弃。
- 改造方向：若需更高吞吐，改成每包独立重发计时器；当前形态别动。

## 七、改造优先级建议

| 优先级 | 项 | 改动量 |
|--------|----|--------|
| P0 | 校验和换 CRC-16 | 中等（协议层一处 + 各板同步） |
| P1 | 入口加地址过滤 | 小（一行） |
| P2 | 文档对齐 SN 实际位数 | 小（文档） |
| P2 | 队列满丢弃改显式日志 | 小 |
| P3 | malloc 换池化 | 中（看现状是否已接近碎片阈值） |
| P3 | 失步恢复优化（转义/缩短窗口） | 中（现场有问题再做） |

---

## 八、给 Agent 的执行要求

1. 改动必须保持"单份协议实现、多板复用"的架构。
2. 任何可靠性行为变更（ACK/去重/合并/广播兜底）前，先确认不破坏上述已验证设计。
3. 改完协议层，必须同步更新设计文档与各板消费逻辑。
4. 涉及电机安全的功能，校验升级到 CRC-16 前不允许交付。
5. 改协议前先读 `ComProtocol.c` 现状，文档描述与实现有出入时以实现为准并回填文档。
