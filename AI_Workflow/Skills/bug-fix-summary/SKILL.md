# Bug 修复总结

把一次具体的 Bug 修复拆成两层：**事实层**（工程相关，记录发生了什么）和
**经验层**（工程无关，提炼可复用的模式）。目标是经验层脱离当前工程也能用。

## 触发约束

- 仅在 `/bug-fix-summary` 显式调用时执行
- 修完 Bug 后禁止主动总结，哪怕改动再大

## 流程

1. **自动收集事实**（禁止只格式化用户口述内容）：
   - `git diff` / `git log` 定位本次修复的实际改动文件、函数、改动点
   - 结合会话上下文确认根因链条
   - 事实不确定的标 `[待确认]` 并向用户求证，禁止编造根因
2. 按下方格式输出两层报告

## 输出格式

### 事实层（工程相关）

- 项目名称：仓库根目录名，自动获取
- Bug 现象：外部可观察到的行为
- Bug 源头：根因，定位到具体 文件:行 / 函数 / 逻辑
- 触发条件：什么输入 / 时序 / 状态下出现
- 解决方法：实际改动点列表

### 经验层（工程无关，可复用）

- 根因分类：从以下类目选取（可多选）：
  并发竞争 / 时序依赖 / 边界条件 / 资源泄漏 / 状态机遗漏 /
  配置不一致 / 硬件理解偏差 / 错误处理缺失 / 数值溢出与类型混用
- 同类隐患：这类 Bug 通常还藏在具有什么代码特征的地方
  （本工程和其他工程都适用）
- 拦截手段：下次如何提前拦住——评审检查项 / 测试用例 / 静态检查，
  至少给出一条可直接执行的

## 禁止事项

- 经验层禁止写"以后要注意""下次小心"这类空话，每条必须可执行
- 禁止为了凑经验层而强行拔高——确实是低级笔误就直说，经验层写"无通用经验"
- 禁止总结未实际修复的问题
