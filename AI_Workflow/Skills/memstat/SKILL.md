# Map 文件与内存预算分析

回答三个问题：RAM 够不够、Flash 够不够、栈会不会溢。
一切结论以 .map / 链接脚本实际数据为准，禁止凭经验估算。

## 第 0 步：拿到输入

- .map 文件路径 + 链接脚本（.ld/.sct/.icf）路径，缺哪个要哪个
- 芯片资源上限：RAM / Flash 总量（查数据手册，禁止编造）
- 没有 .map 时：先告知如何开启 map 输出（编译选项），不硬分析

## 分析流程

### 1. RAM 占用

- 从 map 提取各段占用：.data / .bss / 堆 / 栈保留区，按大小排序
- 找出 Top N 大户：大数组、大缓冲区、协议栈/中间件静态占用
- 核对：总占用 vs RAM 上限，余量是否 ≥ 安全水位（建议 ≥20%）

### 2. Flash 占用

- .text / .rodata / .data 初始值 各多少，Top N 大户
- 常见吞 Flash 项：printf 浮点支持、未裁剪的库、查表数据、
  调试符号残留、重复包含的驱动
- 有 OTA 的工程：核对分区表，APP 区余量是否够下次升级

### 3. 栈分析

- 静态估算：沿最深调用链累加局部变量（重点：ISR 嵌套、
  回调链、递归、大局部数组、printf 族函数）
- 运行时水位：给出栈填充魔术数 + 高水位检测的具体方法
- RTOS 工程：逐任务核对任务栈分配 vs 实际需求

### 4. 常见坑检查

- 大数组进了 .bss 而非 Flash 常量区（缺 const）
- 链接脚本分区余量：各 region 是否贴边，heap/stack 增长会撞上谁
- 对齐浪费：结构体 padding、段对齐损失
- 多份重复符号：同一缓冲被多个模块各定义一份

## 输出格式

```
## 内存总览
RAM:  已用 X / 总 Y（余量 Z%）—— 安全/紧张/超限
Flash: 已用 X / 总 Y（余量 Z%）—— 安全/紧张/超限

## Top 占用项（RAM / Flash 各前 5）
符号名 — 大小 — 所在文件 — 是否可优化

## 栈评估
最深路径 / 各任务栈余量 —— 风险等级

## 优化建议（按收益排序）
每项：改什么 — 预计省多少 — 代价/风险
```

## 禁止事项

- 禁止凭"一般够用"下结论，必须给具体数字和余量百分比
- 优化建议必须带代价说明（砍功能/改算法/加复杂度）
- 优化只报告不动手——实施需用户确认
