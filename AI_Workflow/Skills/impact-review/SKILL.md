# 影响面审查（嵌入式通用版）

改动代码后的系统性复查。核心方法：**以 diff 为起点，顺调用链向外辐射**，禁止无锚点全仓扫描。

## 基本立场

**以找茬心态审查：默认改动有问题，你的任务是找出它，而不是证明它没问题。**
被审查的代码可能就是你上一轮刚写的——更要当别人的代码审。
查完确实没问题，再下「没问题」的结论。

## 第 0 步：确认审查目标

动手前先确定锚点，三者取一：

1. 用户明确指定的文件/函数/commit
2. 未提交改动：`git diff` / `git diff --staged`
3. 用户指定的其他 diff 范围（如 `git diff HEAD~3`）

**`git diff` 为空且用户未指定目标时：停下来问，禁止自己去找"看起来像改动"的东西。**
没有锚点就没有审查。

## 第 0.5 步：入乡随俗

开始审查前，先检查当前项目根目录是否有：

- `AGENTS.md` / `CLAUDE.md` —— 有则遵守其中的范围限制与文档规则
- 设计文档目录（如 `docs/design/`）—— 有则先读模块索引再定位代码

都没有再按本文件的默认流程走。

## 审查流程

### 1. 锚定改动

- 优先 `git diff`（未提交）或用户指定的文件/函数
- **diff 过大时**：按文件/模块分批审查，每批独立出报告；
  优先审高风险项（全局状态、ISR/回调、协议、存储格式），低风险改动（重命名、日志）可合并快速过
- 列出两类改动对象：
  - **函数**：新增/修改/删除
  - **全局状态**：全局变量、标志位、状态机、共享缓冲区、配置宏（Kconfig/defconfig/编译脚本宏）

### 2. 调用链追踪（双向，2~3 跳）

- **向上**：Grep 全部调用方，逐处确认上下文假设未被破坏
  （参数范围、前置条件、调用时机、返回值处理、调用上下文是任务还是中断）
- **向下**：确认被调函数的前置条件/时序在新逻辑下仍成立
- **横向**：对改动的全局状态，Grep 全部读写点，确认无非法状态组合、无读写竞争

**收敛标准**：同一调用方/读写点超过 10 处时，优先覆盖高风险点
（中断上下文、跨模块调用、错误路径），其余抽样；
**未覆盖的范围必须在报告中显式声明**，禁止假装全覆盖。

发现可疑迹象再向外扩，扩之前在报告中写明扩张原因。

### 3. 通用逻辑检查

- **边界**：参数极值、NULL、越界、整数溢出、分支是否全覆盖
- **时序**：是否依赖了不保证的执行顺序（初始化先后、回调次序、事件到达顺序）
- **配对**：申请/释放、使能/除能、开关中断、进出临界区、取/放锁是否成对
- **错误处理**：失败分支是否吞掉错误；错误路径上的资源泄漏
- **数值**：有符号/无符号混用、移位溢出、定点精度、强制类型转换截断

### 4. 嵌入式专项（按相关性逐条过）

**中断与并发**
- ISR/回调上下文中是否新增：阻塞、延时、printf 类日志、堆内存申请、
  Flash 擦写、不可重入函数调用
- 任务与 ISR 共享的变量：是否声明 `volatile`；多字节数据（超过机器字长）
  读写是否有保护，防止 ISR 打断造成的数据撕裂
- 是否引入新的优先级反转/死锁可能

**时序敏感路径**
- 识别项目中的实时路径（通信协议状态机、采样、PWM/灯效刷新、协议窗口期），
  新逻辑是否可能拖延或打乱这些路径
- 中断优先级配置是否与改动后的执行时长匹配

**状态机安全性**
- 新增状态/转移是否完备；异常路径（超时、断连、错误恢复）能否回到安全态
- 是否存在改动能到达但原设计不可能的状态组合

**内存与资源**
- RAM：新增大数组/大栈变量（核对任务栈余量）、堆碎片化风险
- Flash：代码增量、是否往磨损敏感区域新增擦写
- 栈：中断嵌套加深、回调链变长是否会爆栈

**硬件副作用**
- 寄存器/GPIO/时钟/DMA 配置改动：确认不影响共用该外设/引脚/时钟域的其他模块
- 低功耗：改动是否阻止进睡、增加唤醒源、改变电源域状态

**配置一致性**
- 编译宏、Kconfig、构建脚本、源码 #ifdef 多处是否配套
- 条件编译的各分支是否都被审查（不只是当前启用的分支）

**兼容性与数据格式**
- 改动是否影响多硬件版本/多固件版本共存的路径
- 协议/存储格式改动：字节序、结构体对齐与填充、字段长度变化——
  是否破坏向后兼容（OTA 升级、参数区布局尤其注意）

## 输出格式

### 批次头（分批审查时每批必写）

```
## 批次 N：范围说明
- 本批覆盖：文件/模块列表
- 调用链覆盖：全覆盖 / 抽样（未覆盖范围：xxx）
- 跳过项及原因：xxx
```

### 问题条目

按严重程度排序，每条：

[高/中/低] [确认/可疑] 文件:行号 — 问题描述 — 触发条件 — 建议

- **确认**：有明确代码证据
- **可疑**：静态无法证实，标注「需验证」及具体验证方法，用最小模板写清楚，禁止"建议测试一下"这类空话：
  - 仪器：逻辑分析仪/示波器量哪个引脚、什么信号
  - 复现：具体步骤 1-2-3（触发条件、时序、输入）
  - 静态手段：`_Static_assert`、编译期检查、代码评审关注点
- 查完没问题就直说没问题，禁止凑数

## 禁止事项

- 禁止无锚点全仓扫描
- 禁止顺手修复——审查只报告，修复需用户确认
- 禁止报纯风格问题
- 禁止编造硬件行为：涉及未验证的芯片/寄存器行为，一律标「未经测试，需验证」
