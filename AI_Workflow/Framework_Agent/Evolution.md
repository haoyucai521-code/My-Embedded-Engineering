# Framework Agent 版本演进

记录 Framework Agent Prompt 从 1.0 到 3.0 的核心变化。

---

## 版本概述

| 版本 | 核心定位 | 生成文件 | 适用场景 |
|------|----------|----------|----------|
| 1.0 | 约束 Agent 行为 | AGENTS.md | 通用项目 |
| 2.0 | 建立轻量可执行约束体系 | AGENTS.md + PROJECT_DESIGN.md + SOURCEMAP.map + README.md | 通用项目 |
| 3.0 | 面向嵌入式工程的约束体系 | 同 2.0 | 嵌入式工程 |
| 4.0 | 资源约束 + 更新路由 + 冲突裁决（topics 选装） | AGENTS.md + PROJECT_DESIGN.md + SOURCEMAP.map + resource_map.md + README.md（topics/ 选装） | 嵌入式工程 |

---

## 1.0 → 2.0 提升

### 1. 从单文件到体系化

- 1.0 只生成 `AGENTS.md`。
- 2.0 要求生成 4 个文件，形成完整约束体系：
  - `AGENTS.md`：Agent 行为约束。
  - `docs/design/PROJECT_DESIGN.md`：核心设计事实来源。
  - `docs/design/SOURCEMAP.map`：模块定位索引。
  - `README.md`：面向开发者的项目说明。

### 2. 增加项目适配规则

- 区分"项目已有代码"和"项目为空"两种情况。
- 已有代码：基于现有结构总结，不改动架构。
- 空项目：仅定义最小合理结构，不做扩展设计。

### 3. 明确 Agent 行为边界

- 默认只读取当前任务相关文件。
- 默认禁止全仓扫描、无关重构、主动优化。
- 只有在怀疑跨模块、初始化流程、全局状态等问题时，才允许扩大分析范围。

### 4. 引入执行风格与探索预算

- 小步修改、最小可运行改动、一次只处理一个问题。
- 不输出教学内容、不输出未来规划、不重复需求。
- 扩大范围时必须说明原因，优先最小范围探索。

## 2.0 → 3.0 提升

### 1. 增加嵌入式特殊要求

3.0 最大的变化是加入嵌入式工程约束：

- 涉及 DMA、Cache、中断、时钟、引脚复用、功耗、Flash、BLE 事件链、RTOS 任务调度时，必须说明：
  1. 关键硬件约束。
  2. 潜在风险与触发条件。
  3. 规避方案。
- 未经验证的硬件行为必须标注"需验证"。
- 禁止编造寄存器地址、芯片特性、勘误信息。

### 2. 强化代码注释规范

- 代码注释使用中文。
- 注释重点说明：为什么这样做、边界条件、潜在风险、设计原因。
- 禁止无意义注释、重复逻辑注释、描述显而易见行为。

### 3. 文档同步规则更严格

- 任何结构或逻辑变化后，必须同步更新 `PROJECT_DESIGN.md` 和 `SOURCEMAP.map`。
- 代码与设计不一致时，优先更新设计文档。
- 禁止代码长期偏离设计。

### 4. 输出要求更贴合工程

- 保持与现有工程风格和目录结构一致。
- 分文件输出，不解释、不建议、不输出分析过程。

## 3.0 → 4.0 提升

### 1. 新增资源分配表

- `resource_map.md` 成为资源级唯一权威文档。
- 只记分配决策（谁占用、为什么、关联模块），禁止记录具体寄存器值——值的唯一来源是代码。
- 表结构含示例行（Flash 分区 / DMA 通道 / 中断优先级），防止 Agent 对空表发明内容。
- Agent 修改任何资源前必须先查表，拦截编译通过但上板才炸的资源冲突（DMA 通道争抢、中断优先级压过 RTOS 临界区、时钟改动引起外设分频漂移）。
- 表与代码是校验关系而非替代关系：查表后必须以代码现状核对，不一致时以代码为事实、先修表再继续——过期表因此成为漂移检测器，而不是错误权威化的来源。

### 2. 从同步更新到更新路由

- 3.0 要求任何变化同步更新全部文档，是索引漂移的根源。
- 4.0 按变更类型路由到唯一目标文件：资源级 → resource_map.md，模块级 → SOURCEMAP.map，总体级 → PROJECT_DESIGN.md。
- 相同内容只在一个权威文档完整描述，其他位置链接引用。
- 每次变更完成后必须过一遍路由表，确认无遗漏的文档更新，把文档同步从口号变成固定收尾动作。
- 代码与文档同一任务内收敛，未完成文档更新的变更不算完成。

### 3. 新增冲突裁决链

- 裁决顺序：芯片手册 > 已确认需求 > 设计文档 > 代码现状。
- 低层级与高层级冲突时以高层级为准，裁决后先修正权威文档再改代码。
- 禁止以代码现状反向覆盖设计文档，解决 3.0"设计优先"在设计过时时给错答案的问题。

### 4. topics 拆分改为触发式选装

- 3.0 计划的文档拆分在 4.0 改为条件触发：PROJECT_DESIGN.md 超过 500 行时才拆分专题，未触发前不创建目录。
- Agent 每次更新 PROJECT_DESIGN.md 时检查行数，超过 300 行必须拆分并更新路由表，防止触发条件形同虚设。
- 拆分判据：独立演化 / 超 100 行 / 独立验证边界，满足其一才拆。
- 合并规则：两个专题连续三次被同一变更同时修改时合并，防止拆错锁定。
- 禁止占位文档，且定义验收标准：专题含全部四节且合计不少于 50 行才算非占位，防止 Agent 对空文档脑补设计。
- 300 行阈值基于嵌入式工程实测：R157H（MCU+BLE+多模块）设计文档约 400 行，已接近单文件可读性上限；500 行阈值意味着 95% 嵌入式工程永远触发不了拆分，形同虚设。

### 5. 参数化与防漂移补充

- 编码规范来源从写死路径改为 `{CODING_GUIDE}` 占位符，支持多工程复用。
- SOURCEMAP 只登记自研模块，无明确要求不读 SDK 与闭源库源码。
- 修复后必须登记复验结果，不得以未复测的修复结束。
- 发现无关高风险问题时只报告，不修改。

## 核心演进方向

1. **从约束到体系**：1.0 约束行为，2.0 建立完整约束体系，3.0 针对嵌入式领域深化。
2. **从通用到专用**：3.0 增加硬件相关约束，贴近嵌入式开发实际。
3. **从建议到强制**：文档同步、代码注释、事实来源等要求逐步明确和严格。
4. **从过程到结果**：输出要求逐步强调直接给结果，减少解释和教学。
5. **从预设计到按需启用**：4.0 把文档拆分改为触发式选装，重量跟随工程规模增长，不预先支付维护成本。
